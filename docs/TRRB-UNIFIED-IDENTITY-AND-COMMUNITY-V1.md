# TRRB统一用户与互动底座 V1

## 目标
网站、iOS、Android共用一套Supabase Auth、用户资料、评论、点赞、举报、收藏、阅读历史与通知偏好数据。功能可以分阶段上线，但用户ID、评论ID和互动数据不得分裂成多套。

## 注册默认身份
每个新注册用户由数据库触发器自动创建profile：
- 随机中文昵称，由20个前缀×20个后缀组合生成；冲突时自动重试，极端情况下追加6位随机数字。
- 随机默认头像键 `avatar_001`—`avatar_120`。
- `is_custom_name=false`、`is_custom_avatar=false`。
- 用户后续可以修改昵称或头像；所有历史评论通过user_id关联profile，因此会自动显示最新资料。

普通用户不得依靠前端自报管理员身份。平台后续需对“唐人日报、TRRB、管理员、官方、客服、编辑部”等保留词执行昵称校验。

## 数据表
- `profiles`: 统一公开身份。
- `comments`: 新闻评论与回复，`parent_id`支持层级回复。
- `comment_likes`: 一用户一评论一赞。
- `comment_reports`: 一用户对同一评论最多一个举报。
- `favorites`: 登录后的云端收藏。
- `reading_history`: 登录后的跨设备阅读历史。
- `notification_preferences`: 重大新闻、ICE、移民、法律更新、评论回复通知偏好。
- `user_blocks`: 用户屏蔽关系。
- `moderation_actions`: 后台治理审计记录。
- `account_deletion_requests`: 用户账户注销/删除请求，记录来源、状态、申请与完成时间。

## 游客与登录用户
游客可浏览公开新闻和法律内容，并继续使用App本地收藏/历史。登录后再将本地收藏/历史合并进云端，避免强制注册阻塞阅读。

需要登录的互动：发表评论、回复、点赞、举报、跨设备收藏、跨设备历史、个性化推送。

## 账户注销与数据删除（强制上架要求）
只要TRRB App提供账户创建，就必须同步提供账户删除能力。该能力属于V1基础要求，不得作为“以后再做”的可选功能。

### App内入口
- iOS与Android统一提供：`我的 → 账号设置 → 注销账户`。
- 删除入口必须清晰可发现，不得只提供“停用/冻结账户”。
- 用户发起删除前需再次验证当前登录身份，并明确告知将删除的账户与关联数据。
- 用户确认后创建 `account_deletion_requests` 记录，由可信服务端完成最终删除；客户端不得持有service role密钥，也不得直接删除 `auth.users`。

### 网站外部入口
- TRRB网站必须提供一个公开可访问的账户删除页面/申请入口，供无法进入App的用户发起删除请求。
- 该页面后续作为Google Play Console Data safety中的Account deletion URL。
- 网站和App必须进入同一套删除流程，不允许维护两套独立人工表单。

### 删除范围
账户删除完成时，原则上删除：
- Supabase Auth账户；
- profile与自定义昵称/头像资料；
- 评论、回复、点赞、举报；
- 收藏、阅读历史、通知偏好、屏蔽关系；
- 其他直接绑定该user_id且没有合法保留依据的个人数据。

现有核心用户表通过外键 `on delete cascade` 与profile/Auth身份绑定，最终删除流程必须验证这些关联数据被实际清除。

如因安全、防欺诈、法律或监管要求必须保留极少量数据，必须在隐私政策与删除确认页面明确说明保留类别、原因和适用期限。不得以“可能保留”为理由默认保留全部用户数据。

### 删除状态
`account_deletion_requests.status`：
- `requested`: 用户已发起；
- `processing`: 服务端正在执行；
- `completed`: 账户与应删除数据已删除；
- `cancelled`: 用户在完成前主动取消（若产品后续开放取消窗口）。

完成删除的权限只属于可信服务端。普通客户端RLS只允许用户创建并读取自己的删除请求。

## 评论治理
第一版数据模型已经支持 `published / pending / hidden / deleted` 状态、举报和moderation审计。上线发表评论API前必须增加：频率限制、保留词/敏感词治理、封禁检查、服务端身份校验。禁止仅靠客户端隐藏按钮实现权限控制。

## 头像资源
数据库只保存稳定的 `avatar_key`。前端统一将 `avatar_001`—`avatar_120` 映射到TRRB自有头像资源。不得依赖第三方随机头像服务作为生产真源。

## 第一阶段验收
- migration存在并可审计；
- 注册触发器生成profile与通知偏好；
- 随机昵称和头像由数据库统一生成；
- 评论、点赞、举报、收藏、历史、通知、屏蔽、治理表齐全；
- `account_deletion_requests`存在并启用RLS；
- App内注销入口与网站外部删除入口被列为上架前硬性验收项；
- 最终删除必须由可信服务端执行，并验证Auth账户与关联用户数据实际清除；
- 用户数据表启用RLS；
- 网站、iOS、Android后续只允许复用这一套身份主键。
